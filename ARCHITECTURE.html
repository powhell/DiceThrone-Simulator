Dice Throne Simulator · Carte d'architecture · 22 juillet 2026

Le codebase, en une page

Un moteur de jeu Dice Throne (combat aux dés) + une IA, avec deux interfaces navigateur : un coach qui optimise la garde des dés, et un jeu complet contre l'IA. Moteur écrit en TypeScript, bundlé en JS statique. Aucun serveur.

2 moteurs · coach (engine.js) + sim (game-engine.js) 2 réseaux · v4 déployé + v5 recherche 11 héros turn.ts = 4000 lignes, le monolithe

02 Les sous-systèmes

Solveur DP de dés core/

« Cerveau du coach ». Calcule exactement quels dés garder (récursif sur les 32 sous-ensembles × 6ⁿ relances, mémoïsé). Utilisé par le coach ET par le jet offensif du sim.
  • core/evaluator.ts — evalState, calculateOptimalKeep (coach), optimalKeep (sim, 2× plus rapide)
  • core/types.ts — CharacterConfig<S> : chaque héros s'y branche
Piège : caches evMemo/distMemo globaux, jamais vidés seuls. Les clés-string sont le point chaud n°1.

Moteur de simulation

Le moteur autoritaire : joue un tour complet pour n'importe quel héros, résout toutes les habiletés/phases/jetons. Déterministe (héros, graine, policies).
  • sim/turn.ts — LE monolithe (4019 l.). playTurn + résolution de TOUTES les habiletés (grep name.startsWith)
  • sim/types.ts — GameState, PlayerState, Tokens, WindowAction
  • sim/match.ts — runMatch, createInitialGameState, MAX_TURNS=200
  • sim/decision.ts — resolveResponseWindow (couche d'interaction)
  • sim/oracle.ts — completeOffensiveRoll (pont sim↔solveur)
  • sim/rng.ts — tout le hasard passe ici (déterminisme)
Piège : un joueur mort doit poser gameOver+winner, sinon la partie tourne jusqu'à MAX_TURNS (« timeout » = bug, ≠ « nul »).

Données & règles des héros ×11

Trois couches par héros : (1) données de cartes vérifiées, (2) mécaniques de jetons, (3) valeurs EV pour le solveur.
  • sim/data/characters/<xx>/hero.json — SOURCE DE VÉRITÉ (dicePattern, dégâts, cartes). Vérifié vs scans dans characters/<Hero>/
  • sim/hero/<xx>.rules.ts — mécaniques jetons (mb Strengths, bw Time Bomb…)
  • characters/<xx>/constants.ts — valeurs EV CALIBRÉES
Piège : le boardName (« Balestra (ABBB) ») est un IDENTIFIANT — si tu le changes, grep-le partout. Des erreurs de transcription existent (audit 07-21 : 2 corrigées).

IA déployée : value-greedy

L'IA qui joue vraiment (play.html + calibration). Lookahead 1 coup : rejoue chaque coup, évalue l'état résultant avec le réseau v4, prend le meilleur. L'agent le plus fort actuel.
  • sim/rl/valueGreedyPolicy.ts — createValueGreedyPolicy + priors réglés à la main
  • sim/rl/network.ts — forward (v4) / forward2 (v5 2-têtes)
  • sim/rl/features.ts — encodeState v4 (se redimensionne si on ajoute un héros)
  • static/ai-weights.js — poids v4 (window.AI_WEIGHTS)
Note : la garde de dés est déléguée au solveur DP exact, pas au réseau.

Strong-AI (AlphaZero) expérimental

Agent MCTS self-play sur réseau 2-têtes à layout stable. Objectif : dépasser value-greedy. État : ~33 % vs value-greedy, ne cliquette pas encore (voir JOURNAL_STRONG_AI.md).
  • sim/rl/featuresV5.ts — layout FIGÉ (ajouter un héros ne re-dimensionne pas → warm-start)
  • sim/search/gameNode.ts — LE seam : convertit le PUSH du moteur en PULL pour la recherche
  • sim/search/mcts.ts — MCTS/PUCT
  • sim/search/{selfplay2,gate3}.ts — génération self-play + gating
  • rl-py/{train.py,chain2.mjs} — entraînement PyTorch + boucle de générations
Piège : tests à 88 parties = ±10 % de bruit. Pour « bat-on X ? » → 400+ parties obligatoires.

Calibration EV

Mesure la valeur (en équivalent-dégâts) de chaque jeton/carte par parties appariées contrefactuelles (même graine, un seul changement d'état initial). Alimente les constants.ts.
  • calibration/{arms,run,worker,analyze}.mjs — bras (mutations), lanceur //, worker, analyse
  • calibration/matrix_team.mjs — matrice de win-rates (méta)
Piège : worker.mjs lit static/game-engine.js → rebuild le sim après une modif moteur, sinon calibration périmée. ≤4 workers (thermique).

🧠 Entraînement strong-AI

chain2.mjs→selfplay2 (MCTS+GameNode)→train.py (GPU)→gate3 (candidat vs champion)→promotion

04 Comment ajouter / réparer

Réparer un motif de dés erroné (comme Balestra/Pyroblast)
  1. Vérifier contre le scan physique dans characters/<Hero>/board/ ou /cards/
  2. Éditer hero.json (dicePattern + boardName)
  3. grep le boardName PARTOUT et corriger tout (abilities.ts, play.js, SPEC.md, textes des cartes upgrade)
  4. tsc --noEmit + vitest run, puis rebuild game-engine.js + gen-assets
Empêcher l'IA de décider à la place d'un humain (choix pré-armé)
  1. Ajouter un champ pref à PlayerState dans sim/types.ts
  2. Dans le code de résolution : if (humanControlled && pref) use pref; else heuristique IA. L'IA ne pose JAMAIS la pref (comportement calibré inchangé).
  3. Bouton cyclique dans play.js renderControls (modèles : addMbBtns, addFmDefBtns)
  4. rebuild game-engine.js
Ajouter un héros (résumé)
  1. Scanner board+cartes → characters/<Hero>/ + SPEC.md
  2. sim/data/characters/<xx>/hero.json + sim/hero/<xx>.rules.ts + characters/<xx>/{config,abilities,constants}.ts
  3. Câbler la résolution dans sim/turn.ts, enregistrer dans load.ts / oracle.ts
  4. Strong-AI : append à featuresV5 (HERO_REGISTRY + jetons) + matchups.ts (warm-start-safe, FEATURE_COUNT_V5 reste 223)
  5. Tests, rebuild, boutons play.js, calibrer les jetons

05 Les 6 pièges à connaître

REBUILD après édition. static/*.js embarquent le TS + le JSON des héros. Édite la source → rebuild (game-engine.js via esbuild browser.ts ; engine.js via npm run build) ou les UIs/calibration tournent périmés.
Deux moteurs, deux réseaux. engine.js (coach, HH/BW/FM) vs game-engine.js (sim, 11 héros). v4 (déployé) vs v5 (recherche). Ne pas confondre.
Le déterminisme est le contrat. Tout le hasard passe par sim/rng.ts. Même (héros, graine, policies) → même partie. Le seam GameNode en dépend.
Honnêteté statistique. Un A/B de 88 parties porte ±10 % d'erreur — ne jamais conclure « on bat X » là-dessus. 400+ parties (leçon apprise, JOURNAL_STRONG_AI.md).
CPU / thermique. ≤4 workers pour les runs longues ; risque de CPU à 100° en empilant des batches. Plan « Performances élevées » + surveiller les temps la nuit.
Le JSON héros = vérité, mais des erreurs de transcription existent. Vérifier contre les scans characters/<Hero>/ (audit 07-21 : Balestra + Pyroblast corrigés).
Version machine (pour le prochain agent) : ARCHITECTURE.json · Build/conventions : CLAUDE.md · Strong-AI : PLAN_STRONG_AI.md + JOURNAL_STRONG_AI.md · engine-ts/src ≈ 15 000 lignes TS.
